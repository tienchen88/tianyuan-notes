讓 agent 自己修自己的 harness，Cole Medin 這次說得比較保守

Cole Medin 昨天一口氣上了兩支，另一支講安全的在這裡。這篇是 Let Your AI Agent Do ITS OWN Harness Engineering (Here's How)。

一樣還沒看。資料來自一篇整理文，它沒寫出片名，只說是 Cole 的片、用 LangChain 的 Managed Deep Agents 當例子，日期對得上，應該就是這支，但我不敢百分之百確定。

harness 是什麼

他之前講過，模型只是一層，外面包的那層才決定 agent 實際好不好用。全域規則、skill、MCP 工具、hook、subagent，這些加起來叫 harness。

這次往前走一步：這層東西，能不能讓 agent 自己改。

兩個迴圈

整理文把做法拆成兩個迴圈。

第一個是當下的。agent 碰到拿不準的情況，先給一個暫定答案，丟給人確認。人改過的答案存起來當記憶，下次類似情況可以撈出來用。它舉了一個 Archon 客服 agent 的例子：agent 去搜主分支的程式碼，沒看到使用者在自己分支上已經修好的東西，被人糾正之後記下了那個分支和修正的位置，後來相關的問題就答得出來了。

第二個是事後的，比較慢。回頭翻整段的互動紀錄，找反覆出現的錯，然後提議改 instruction、skill 或 guardrail。

我覺得這個分法有道理。單一案例的教訓放記憶就好，會一直重複的才值得改規則。兩種都塞進規則檔，規則檔很快就會長成一坨。

他沒有說放手

標題聽起來像是 agent 自己把自己調好，可是整理文寫的保護措施蠻多的：提議的改動要人看過，要拿一批有代表性的案例測，真的重要的檢查交給寫死的 hook，改動一點一點放，放完再盯紀錄有沒有退步。

上禮拜他才收回了暗燈工廠，說 agent 自己審自己常常只是把原本的錯再確認一次。這次讓 agent 改自己的 harness，照理也會碰到同樣的問題，所以人審這一步留著，我不意外。

還有一個巧合。前幾天看 Matt Pocock 那包 skill 的更新，新加了一個 retro，做完事回頭檢討環境。跟這裡的第二個迴圈幾乎是同一件事。兩邊差不多同時走到這裡，可能代表大家都卡在同一個地方：規則寫完之後，誰來維護。

想在片裡找的

一是 agent 提議的改動，命中率大概多少。如果十條裡人只收一兩條，那審的成本可能比自己寫還高。整理文也承認沒有任何數字。

二是規則檔越改越長之後，他怎麼處理。只加不減的話，遲早會互相打架。

三是 LangChain 那套是不是必要。整理文說這個模式跟平台無關，我想知道用一般的 coding agent 加幾個 hook，能不能做到差不多的事。
