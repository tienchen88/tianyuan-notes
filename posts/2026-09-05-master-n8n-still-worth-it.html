拉節點還值得學嗎？Gary Chen 這支把前提翻出來問

晚上照例去看看有沒有新片，Gary Chen 上了一支：Make 跟 n8n 還值得學嗎？2026 年新手現在該把時間花在哪。這題我一直有點兩邊擺盪，所以先點開來看，結果只看了開頭跟章節列表就先跑來寫了——因為他排的那個順序，比我自己想的清楚。

他把問題問在哪一層

一般人吵這題都是在吵工具：n8n 開源、可以自架、節點多；Make 介面漂亮、上手快；Zapier 貴但穩。這種比較網路上一抓一大把，看完還是不知道自己該不該花時間。

他不從那裡切。看章節，他前面兩段先講「當年為什麼這麼好用」，然後第三段直接跳到「前提變了，維護換人」。片子的說明欄那句話講得蠻白的：不會寫程式的人靠拉節點第一次做出自己的自動化，但這套邏輯有個前提，就是建流程、盯維護的人是我們自己。當 coding agent 能自己讀程式碼、跑測試、看日誌，這個前提就變了。

我覺得這個角度是對的。低程式碼工具真正賣的從來不是「不用寫程式」，是「你自己看得懂、自己修得動」。那個視覺化畫布的價值，一半在建的時候，一半在三個月後你忘光了打開來還認得出流程長怎樣。如果維護這件事整個交出去了，畫布這半的價值就縮水。

「Agent 討厭拉節點」這段我很想聽

七個章節裡我最想聽的是 4:31 那段。因為這件事我有點感覺但講不清楚。

拉節點的產物是一坨 JSON，節點之間靠座標和連線 id 綁在一起。人看畫布很順，但那份 JSON 對模型來說不好處理——改一個地方要同時對到好幾處，而且改完沒辦法用一般的方式 diff，你很難一眼看出它到底動了什麼。反過來，同一個流程如果是幾十行腳本，agent 讀它、改它、跑它、看報錯，整條路都是它熟的。

所以這裡的落差不在「誰比較會做自動化」，是在載體上。同一件事換一種存法，一邊變難一邊變簡單。

不過我也不想把話講死。有些東西 n8n 是真的省事——現成的 OAuth 串接、重試、排程、還有一個一直開著的執行環境。這些你自己寫腳本都要重來一遍，而且很容易寫得比人家爛。網路上有篇整理講得蠻實在的：很多人要的自動化根本不需要 AI 介入，收到信就觸發、資料搬個位置、定時發通知，這種事 n8n 做起來比塞一個模型進去穩定太多。

舊流程要不要搬

9:39 那段是「舊流程什麼時候才值得搬」。我猜他會給條件而不是給結論，希望是這樣。

我自己的直覺是：能跑就別動。已經在跑、沒在出包、你也不常改的流程，搬過去只是把一個穩定的東西換成一個要重新驗的東西，換來的好處還說不準。真正該考慮搬的大概是那種你每個月都要進去改、改完還會壞、壞了要花半天看是哪個節點的——那種流程本來就已經是負債，只是它長得很像資產。

我的保留

有一點我還沒被說服：agent 接手維護這件事，聽起來像是把負擔拿掉，實際上是換了一種負擔。以前你維護流程，至少你知道它長怎樣；現在你維護的是一套讓 agent 看得懂的東西——說明檔、測試、日誌格式。這些也要人寫、也會過期、也會腐爛。

這半年我被這件事繞進去好幾次。以為把手工活交出去就輕鬆了，結果只是換成在維護另一層。所以「還值不值得學」這題，我傾向的答案是：學，但不要學成「n8n 專家」。把它當成一個知道什麼時候該用的選項，別把它當成你唯一會的那把工具。

最後一段 11:41 講「怎麼跟 AI 開口」，那是給完全沒技術背景的人的。這段我反而覺得最實用——因為卡住多數人的從來不是工具選哪個，是不知道第一句話該怎麼講。
