Matt Pocock 那包 skill 又改版了，我先去翻了 changelog

Gary Chen 昨天上了 28 萬星的 Matt Pocock skill 更新拆解！。

片我還沒看。看到標題就先跑去 mattpocock/skills 翻了一下，現在顯示大概 29 萬多星，比標題寫的又多了一點。下面是我自己讀 README 和 CHANGELOG 整理的，不是片裡講的，他拆的重點可能跟我抓的不一樣。

這次改了什麼

照 changelog，最近一個 minor 版是 1.3.0，後面再補了一個 1.3.1 的小修。我覺得比較有份量的是這幾個：

  • 新增 implement-spec：一整份 spec 在一條 branch 上跑完，用 task graph 排順序，每張工單開自己的 worktree，最後收在 code-review
  • 新增 pr：規定 PR 內文要有摘要、證據、合併風險判斷
  • 新增 retro：一次工作結束後，回頭建議環境該怎麼改，嚴重的排前面
  • 拿掉 resolving-merge-conflicts
  • CONTEXT.md 改名叫 GLOSSARY.md，舊專案要自己 git mv

還有一個小細節：他把整個 repo 文字裡的破折號全拿掉了。另外有六個 skill 的 description 因為 YAML 沒加引號，導致安裝工具找不到它們，這次也一起修了。

我比較在意的兩點

第一個是 implement-spec 跟原本 implement 的分工。原本的流程是先 /to-spec 寫規格、/to-tickets 拆成工單，再一張一張做。現在多一條路，直接把整份 spec 丟進去平行跑。

這跟昨天寫的那種「軟體工廠」思路有點像，只是他的版本前面還卡著一道 /grill-with-docs，人要先被問到每個分支都講清楚才往下走。老實說我覺得這個順序是對的。只是 worktree 一多，最後合起來的時候衝突怎麼處理？剛好他又把處理 merge conflict 的那個 skill 拿掉了，這兩件事放在一起看我有點不懂。可能是 task graph 排好依賴之後衝突本來就少，也可能是他覺得這件事不需要獨立一個 skill。這個我想聽 Gary 怎麼解讀。

第二個是改名。CONTEXT 變 GLOSSARY 看起來只是換字，但其實是在講這份檔案的用途：它是一份名詞表，讓人跟 agent 對同一個詞有同一個意思，wait-what 重新解釋訊息的時候也是拿這份來用。同一個概念前後用三種講法，人大概看得懂，換成 agent 就容易岔開。

retro 這個

retro 是這次新增裡我最想多看一下的。做完一件事回頭想「下次環境該怎麼調」，把它變成一個固定指令，等於每次收尾都會被提醒一次。

不過它建議出來的東西誰來決定要不要改，README 上看不太出來。如果 agent 自己提、自己改，那又回到自己審自己的老問題。

想在片裡找的

一是 Gary 怎麼看 implement-spec 跟 implement 的取捨，什麼規模的需求該走哪條。

二是他有沒有實際裝起來跑過 1.3 版，還是只是讀 changelog。如果有跑，retro 吐出來的建議長什麼樣我很好奇。

三是升級的實際成本。改名那一項對已經在用的人不是零成本，不知道他有沒有提到。
