同一批 150 筆，用序號指它錯 86 次，換成鍵名錯 0 次

Gary Chen 今天上了 Jev + Claude，男女搭配，幹活不累。

片還沒看。Jev 這個月我已經寫過解析那支、用在 coding 的、接第二大腦的，倍率那兩個數字拆過一次就夠了。這次標題講的是搭配，所以我去翻接法——到底接在哪一層、誰來維護那條分工線。下面是我自己查的，不是片裡的內容。

四條接法，侵入程度差很多

目前比較成形的有四種。

最輕的是官方那個 agent skill，裝完之後教 Claude Code 把好幾個問題攤成一次呼叫。第二種是掛在邊界上的 hook，PreToolUse、compaction、stop 這幾個點，社群的 jev-axi 就是拿它擋危險指令，常規指令走本地規則，可疑的才送出去問一次，有人自己量是大約 375 毫秒、一次篩選 0.00004 美元。第三種走 MCP，把 jev_verify、jev_screen、jev_classify、jev_gate 這類判斷註冊成工具，讓模型在推理中途自己叫。最重的是每一輪都做模型路由，一個 proxy 夾在 CLI 跟模型中間，每輪先問 Jev 一次該用哪個等級的模型，真正寫程式的還是前線那顆。

四條的共同前提是 Jev 取代不了底層那顆大的。它收 state 加上有型別的問題，回結構化的答案跟機率，連線路格式都跟 Messages API 不相容，所以「改個 base URL 就好」這種想法不用試。

那個 86 次

有人做了一份實測，列出官方文件沒寫的一個坑：在長清單裡用位置序號指涉項目，不可靠。

官方範例裡有 candidates[i] 這種寫法。他量出來的是：150 筆一次問、用序號指，320 題裡錯 86 題；清單縮到 25 筆，還是錯 29 題。換成具名的鍵（candidates.k137），150 筆一次問，320 題錯 0 題。把項目直接嵌進它自己那一題裡面，320 筆一次問，錯 0 題，0.4 秒。

這個坑討厭的地方在於它不是判斷錯。模型對那段文字的判斷可能完全正確，只是它把答案掛到隔壁那一筆上去了。輸出是結構化的，型別也對，所以不會報錯，看起來就是一份乾乾淨淨的結果。

另外，清單縮短只讓它從 86 降到 29。這代表它不是「批次開小一點就安全」的那種問題，是指涉方式本身的問題。我如果自己接，大概會踩過一次才想到要去查這件事。

搭配裡最容易壞的那一環

官方 skill 存在的理由寫得很誠實：他們自己的文件說，coding agent 比人更容易掉進「一題一次呼叫」的習慣。

這句話我覺得要停一下。整套便宜建立在攤平上——同一次呼叫裡塞 13 個獨立問題，有人量出來比拆成 13 次便宜 12.2 倍、快 10 倍。而會不會攤平，決定的是那個 agent 自己。

所以分工這件事有個套圈的地方。誰決定哪些事丟給便宜的小模型？如果是人，那是個設計決策，會被想清楚；如果是 Claude 臨場決定，那負責維護這條線的，正好是你想少用一點的那個東西。官方得專門出一個 skill 來矯正它的習慣，大概就是因為放著它自己決定會壞。

「男女搭配」這個比喻裡，分工表是誰寫的，我覺得比分工內容重要。

失敗要往開的方向倒

四種接法的資料裡都反覆講一件事：Jev 掛掉的時候必須 fail-open。判斷服務失效就凍住整個 CLI，通常比放過一次誤判更糟。

這條我同意，但它跟拿 Jev 當 gate 的用法有張力。如果連不上就一律放行，那這個 gate 的功能是雜訊過濾，不是安全機制。它降低的是你每天要親眼看的量，風險上限沒有動。

這剛好接回我十月六號寫 Mods 跟八號那篇的同一個結論：永遠危險的那些動作，規則就寫死在程式裡；要看上下文才知道危不危險的，才交給它判斷。fail-open 可以接受的前提是，真正該擋的東西根本不在這條路上。

信心不是正確率

還有一條我每次都想抄一遍。那個機率講的是分佈有多尖，用來決定什麼時候自動放行、什麼時候升級給人看，它不等於「這一題有多少機率是對的」。校準是按群體算的——標成 0.8 的那一堆裡大約八成會成立，不保證你眼前這一筆。

文件自己還寫了一條：涉及計算的區域不可靠。所以數數、算日期這類不要路由給它，接得再漂亮也不行。

我想在片裡找什麼

一是他選哪條接法。最輕的那條裝完就能用，最重的那條要在 CLI 前面架 proxy，如果他示範的是最重的那條，片名裡的搭配指的其實是另一回事。

二是分工表誰寫。如果做法是「叫 Claude 自己判斷什麼該丟給 Jev」，我會想知道他有沒有量過它判斷得準不準。

三是他有沒有踩過序號那個坑。那種錯法很安靜，跑起來一切正常，做過的人跟沒做過的人講出來的話會不太一樣。
